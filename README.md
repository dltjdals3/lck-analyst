# LCK 경기 데이터 분석 리포트 에이전트

LCK 프로 경기 데이터를 자연어로 질문하면 통계 분석과 리포트 초안을 만들어주는 AI 에이전트.
LangGraph Supervisor 패턴 + Streamlit.

**핵심 설계: 통계 계산은 pandas가 전부 수행하고, LLM은 계산된 숫자를 해석해 문장으로 옮기는 일만 한다.**

---

## 왜 이렇게 만들었나

LLM에게 데이터를 통째로 주고 분석을 시키면 숫자를 지어낸다.
개발 과정에서 실제로 겪은 사례들이다.

| 상황 | LLM의 반응 |
|---|---|
| 시험까지 남은 일수를 안 알려줌 | "약 10개월 남았습니다" (실제 15일) |
| 연도별 성적만 주고 합계를 안 줌 | "총 179경기에서 179승 148패" (실제 327경기) |
| 챔피언을 식별 못 한 채 선수 전체 지표를 넘김 | 그 수치에 챔피언 이름을 붙여 답변 |
| 표본 5경기 챔피언의 승률 | "승률 100%, 저평가된 챔피언" |

공통점은 **LLM이 빈칸을 못 견딘다**는 것이다.
그래서 이 프로젝트는 판단이 필요한 지점을 최대한 파이썬으로 옮겼다.

- 통계 계산 → pandas 고정 함수 (LLM이 코드를 생성해 실행하는 방식은 사용하지 않음)
- 표본 충분성 판단 → 파이썬이 등급을 매기고 서술 지침 문장까지 생성
- 팀·선수·챔피언 이름 식별 → 문자열 매칭, LLM 변환 시에도 실제 목록과 대조 검증
- 분석 종류 선택 → 미리 정의한 메뉴에서만 선택 (자유로운 컬럼 지정 금지)

| 파일 | 내용 |
|---|---|

| `lck_players.csv` | 13,860행 (경기당 선수 10행) |
| `champ_stats.csv` | 연도별 챔피언 픽/밴/승률 집계 |

### 데이터 구조상의 함정

원본은 경기당 12행(선수 10 + 팀 요약 2) 구조라 분리하지 않고 집계하면 선수 기록과 팀 합계가 섞인다.
그 외에 이 데이터를 다룰 때 반드시 알아야 하는 특성들:

- **팀 행은 짝(pair)** — 한 팀이 이기면 상대는 반드시 진다. 승/패가 정확히 50:50이 되며, 이는 구조적 결과지 승률이 아니다. 표본 독립성이 성립하지 않아 상관·검정 결과가 부풀려진다.
- **밴픽률과 승률은 거의 무관** — 상관계수 r = −0.09 (R² = 0.008). 많이 밴픽되는 챔피언이 강한 챔피언은 아니다.
- **드래프트 규칙이 2026 Cup부터 변경** — 이전에는 블루 진영이 곧 선픽이었으나, 이후 선택권을 가진 팀이 진영과 픽 순서 중 하나를 고른다. 두 시기를 합쳐 집계하면 서로 다른 제도의 결과가 섞인다.

### 품질 진단이 잡아내는 것

결측치가 0인 데이터라 일반적인 결측 처리 대신 다른 항목을 진단한다.

- **구조적 결측 vs 실제 결측** — 팀 행에 선수 컬럼이 비어 있는 것은 정상이다. 두 데이터셋을 대조해 자동 판별한다.
- **시간 의존 결측** — `atakhans`는 2024년에 100% 결측. 그해에 존재하지 않던 오브젝트다.
- **편향 결측** — `goldat25` 계열의 결측 행은 평균 경기시간 22.9분, 비결측 행은 32.5분. 25분 전에 끝난 경기라 값이 없는 것이므로, 결측 행을 지우면 접전 경기만 남아 표본이 편향된다.
- **자료형 오인식** — 0/1 이진 컬럼이 숫자형으로 저장돼 평균이 "선취 비율"로 읽혀야 하는 경우.

## 분석 사례

### 결과 누수(leakage) 지표 분리

승패와의 상관계수 상위는 `towers`(r = +0.897)지만, 이는 예측 지표가 아니다.
타워를 모두 부수면 그 자체가 승리이므로 승리를 다르게 센 값에 불과하다.
측정 시점을 기준으로 지표를 분류해 예측 가능한 것만 순위에 넣었다.

| 구분 | 지표 | r |
|---|---|---|
| 예측 지표 | golddiffat15 | +0.508 |
| | xpdiffat15 | +0.474 |
| | firsttower | +0.361 |
| 결과 누수 | towers | +0.897 |
| | dragons | +0.596 |

### 저평가/과대평가 챔피언 탐지 — 기준을 데이터로 교체

당초 설계는 "밴픽률 대비 승률의 잔차"였으나, 실제로 계산하니 R² = 0.008로
회귀선이 사실상 수평선이었다. 잔차가 단순 승률 순위와 같아져 지표로서 의미가 없었다.

그래서 교란 변수를 바꿨다. 챔피언 승률에는 **그 챔피언을 고른 팀의 전력**이 섞여 있다.

```
기대 승률 = 그 챔피언이 픽된 경기에서, 픽한 팀의 시즌 승률 평균
잔차     = 실제 승률 − 기대 승률
```

보정 전후로 순위가 실제로 바뀌었다.

| 챔피언 | 승률 | 기대 승률 | 보정 전 잔차 | 보정 후 잔차 |
|---|---|---|---|---|
| Vayne | 73.3% | 61.5% | +22.4%p (1위) | +11.8%p (7위) |
| Aatrox | 31.2% | 56.0% | −20.1%p | −24.8%p |

Vayne은 강팀이 주로 고른 챔피언이라 순위가 내려갔고,
Aatrox는 강팀이 골랐는데도 졌기 때문에 더 나빠졌다.

### 드래프트 규칙 변경 자동 탐지

규칙 변경 시점을 코드에 명시하지 않고, 진영과 픽 순서의 일치율로 판정한다.

```
2024: 결합 (일치율 100.0%)
2025: 결합 (일치율 100.0%)
2026: 분리 (일치율  71.9%)
```

분리된 시기에만 2×2 교차 분석이 가능하다.

| 조합 | 경기 | 승률 |
|---|---|---|
| Blue + 선픽 | 98 | 60.2% |
| Blue + 후픽 | 251 | 55.8% |
| Red + 선픽 | 251 | 44.2% |
| Red + 후픽 | 98 | 39.8% |

단, 이 2×2는 독립된 네 칸이 아니다. 블루+선픽 팀의 상대는 반드시 레드+후픽이므로
대각선 두 칸의 승률 합은 100%가 되며, 실질적으로 독립된 값은 두 개뿐이다.
또한 진영과 픽 순서는 팀이 선택한 결과이므로 조합별 승률에는 그 자리에 앉은 팀의 전력이 섞여 있다.

## 표본 등급

표본 수에 따라 파이썬이 등급을 매기고, **서술 지침 문장까지 생성해 프롬프트에 넣는다.**
LLM에게 "표본이 충분한지 판단하라"고 맡기지 않는다.

| 표본 | 등급 | 처리 |
|---|---|---|
| 30+ | 표본충분 | 통계적으로 의미 있는 차이로 서술 허용 |
| 10~29 | 표본참고수준-단정금지 | 경향만 언급, 단정 금지 |
| 5~9 | 표본부족-해석금지 | 숫자만 제시, 해석 금지 |
| <5 | 표본매우부족-비율산출금지 | 승률 계산 자체를 하지 않음 |

5경기 이상이어도 변동폭을 함께 제시한다.

```
Cassiopeia  5경기 5승  승률 100.0%
  현재 100.0% / 1패 추가 시 83.3% / 1승 추가 시 100.0%
```

## 구조

```
lol_analyst/
├─ analysis.py      pandas 분석 함수 10종 + 차트
├─ agent.py         LangGraph State / 노드 / 그래프
├─ app.py           Streamlit UI
└─ data/            전처리된 CSV 3개
```

### LangGraph 흐름

```
supervisor ─┬─ profile        데이터 품질 진단
            ├─ analyze        8종 메뉴 중 선택 후 실행
            ├─ report         이번 세션 분석 결과 종합
            └─ out_of_scope   범위 밖 질문 (LLM 호출 없이 고정 안내)
                    └─ final
```

`supervisor`의 LLM 판단 위에 파이썬 보정을 얹었다.

| 조건 | 전환 |
|---|---|
| profile인데 팀·선수·챔피언이 지목됨 | → analyze |
| report인데 리포트 키워드가 없음 | → analyze |
| out_of_scope인데 실제 대상이 지목됨 | → analyze |

State는 호출마다 새로 만들어지므로, 세션 기억은 `st.session_state`에 보관했다가
다음 호출의 초기 State로 다시 넣어준다. `report` 노드는 이 누적 기록을 사용한다.

## 실행

```bash
# 1. 의존성
pip install -r requirements.txt

# 2. 상위 폴더에 .env 생성
#    OPENAI_API_KEY=sk-...

# 3. 데이터 전처리 (Oracle's Elixir 원본 CSV 필요)
python prep_lol.py --check    # 컬럼·팀명 차이 진단
python prep_lol.py            # data/ 생성

# 4. 분석 함수 단독 검증 (LLM 없이 숫자만 확인)
cd lol_analyst
python analysis.py

# 5. 실행
streamlit run app.py
```
